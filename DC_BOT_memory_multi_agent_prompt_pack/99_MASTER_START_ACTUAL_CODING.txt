NON-NEGOTIABLE IMPLEMENTATION RULES

1. Discord IDs, not names, identify Discord accounts.
2. Same-name people must never merge.
3. Text and voice actor identity must converge on the same durable Discord identity.
4. Event-local display snapshots and current aliases are distinct.
5. Group input preserves each speaker separately.
6. Never store "Discord group" as a person.
7. Physical and logical rooms are distinct.
8. DMs, guilds, people, characters, and unbound rooms must remain isolated.
9. Generation and external delivery are separate states.
10. Database and Discord delivery are not falsely treated as atomic.
11. Context eligibility follows approved delivery semantics.
12. A response may causally depend on several user events.
13. Sequence order is not claimed to equal causal awareness.
14. User facts require approved provenance.
15. Corrections supersede stale facts.
16. Unknown facts produce abstention.
17. Retrieved memory is escaped, bounded, and treated as untrusted data.
18. Heavy memory work stays outside the voice-critical path.
19. Production writes must not silently disappear into an ephemeral fallback.
20. Deletion must propagate to approved derived stores and caches.
21. Do not add vectors, learned reranking, or graph infrastructure before their benchmark gate.
22. Preserve existing cancellation, response epoch, TTS ordering, and playback invariants unless an approved specification changes them.
23. Do not collect unrelated guild messages merely to populate memory.
24. Do not enable new Discord intents without the approved operational and privacy change.

IMPLEMENTATION STRATEGY

Work from the approved backlog, but prefer the smallest vertically testable increment.

Recommended implementation waves, subject to approved artifact decisions:

WAVE A — BASELINE AND TEST HARNESS

- Record current commit.
- Verify repository instructions.
- Add or update evaluation fixtures for current defects.
- Add contract tests and failure-injection scaffolding.
- Do not change production behavior until baseline tests exist.

WAVE B — DOMAIN CONTRACTS

- Introduce transport-neutral types and ports.
- Define Person/external identity, actor snapshot, room IDs, events, relations, generation, delivery, and context types.
- Add runtime validation where approved.
- Keep old interfaces behind explicit transitional adapters.

WAVE C — PERSISTENCE FOUNDATION

- Add approved migrations and repository adapter.
- Implement idempotent event append.
- Implement causal relation storage.
- Implement delivery state and reconciliation records.
- Implement outbox only if approved.
- Add concurrency and migration tests.

WAVE D — IDENTITY AND SCOPE PROPAGATION

- Propagate actor snapshots through text and voice.
- Refresh voice actor metadata at speaking start.
- Use the actual voice-channel ID.
- Implement current alias observation with low write amplification.
- Implement safe address rendering.
- Add same-name and scope-isolation tests.

WAVE E — TEXT AND VOICE INTEGRATION

- Replace separate production history ownership with the approved MemoryPort.
- Preserve one event per contributing speaker.
- Remove durable synthetic group authors.
- Preserve text-send and voice-playback delivery semantics.
- Add restart and duplicate-event tests.

WAVE F — CONTEXT ASSEMBLY

- Assemble participant directory, attributed recent turns, and approved summaries.
- Serialize context safely.
- Preserve stable system prefix.
- Add prompt-injection and internal-ID emission tests.
- Enforce deadlines and approved degraded behavior.

WAVE G — EXPLICIT MEMORY AND SUMMARIES

- Implement remember/correct/forget and alias commands.
- Implement provenance and supersession.
- Add background summaries outside the voice path.
- Implement invalidation/regeneration and deletion propagation.

WAVE H — STRUCTURED RETRIEVAL

- Implement authorized exact and lexical retrieval.
- Implement temporal validity and contradiction handling.
- Implement multilingual behavior required by the specification.
- Add abstention and irrelevance tests.

WAVE I — OPTIONAL FEATURES

Only enter when the approved benchmark gate passes:
- Vector retrieval.
- Learned reranking.
- Graph storage/traversal.
- Relationship hypotheses.
- Remote service extraction.

STOP CONDITIONS

Stop the affected workstream and report a blocker when:

- Identity can merge on name or alias.
- DM or cross-guild leakage is possible.
- Delivery semantics are undefined.
- Deletion requirements cannot be met.
- A migration would invent historical attribution.
- A production fallback would silently lose writes.
- Approved artifacts conflict on a release-blocking point.
- A required Discord intent change lacks approval.
- The proposed patch is based on a file version you could not verify.
- Vector or graph work lacks its benchmark gate.
