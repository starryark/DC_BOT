SOURCE-PLAN BASELINE

The documentation program is preparing a full shared-memory implementation for DC_BOT. The source plans propose the following broad direction:

1. Text and voice should stop owning unrelated process-local histories and should use one coherent memory authority through a transport-neutral MemoryPort.
2. The initial deployment topology is not pre-decided. It may be an in-process domain/application layer with SQLite or PostgreSQL, or a standalone Memory Runtime later. A mandatory HTTP microservice must be justified by verified deployment needs.
3. Discord user ID is the durable Discord identity key. Usernames, global display names, guild nicknames, aliases, avatars, and voice characteristics are attributes, not identity keys.
4. Every inbound text or voice event used by the bot should carry a Discord actor snapshot containing the user ID and the best available presentation fields.
5. Current identity and historical presentation must be distinguishable. Old events preserve the name displayed at the time; current addressing uses the active permitted alias.
6. Preferred aliases are scoped. Candidate scopes include platform, character-global, guild, logical room, and private conversation. Private aliases must not leak into public guild contexts.
7. Two people with the same alias must never merge. Prompt-local opaque person references should distinguish speakers while never being printed or spoken.
8. Group voice input must preserve one attributable user event per speaker. The durable author must never be a synthetic person such as "Discord group."
9. Physical Discord rooms and logical conversation rooms are distinct. Recent room history crosses channels only through explicit or configured bindings.
10. Person-level memory may cross text and voice when scope permits, without copying an entire text transcript into a voice room.
11. Raw attributable events, recent context, summaries, semantic memories, episodic memories, and operator-authored procedural memory are separate layers.
12. Durable facts require provenance, confidence, temporal validity, and correction/supersession behavior. Assistant speculation must not become user truth.
13. Delivery must be modeled separately from generation and persistence. A Discord send or voice playback cannot be atomically committed with a database transaction.
14. An assistant response may be triggered by several user events. The data model must support many-to-many causal relations rather than assuming one user event per exchange.
15. Interrupted, failed, unheard, or partially delivered assistant output must not be treated as a normal completed conversational turn.
16. Retrieved memory is untrusted data, not instructions. Prompt serialization must resist delimiter injection, fake-role injection, mentions, Unicode abuse, and internal-ID exposure.
17. Retrieval should begin with authorization, exact structured lookup, temporal filtering, and lexical/full-text search. Vectors, learned rerankers, or graph storage require benchmark evidence.
18. Summarization, extraction, embedding, graph construction, and contradiction reconciliation must remain outside the voice-critical path.
19. DMs, guilds, people, characters, logical rooms, and unbound channels require explicit isolation and authorization rules.
20. Forget, correction, export, retention, backup handling, cache invalidation, summary regeneration, and embedding deletion must be specified before broad production retention.
21. The implementation must be benchmarked for identity continuity, attribution, temporal updates, abstention, privacy leakage, deletion completeness, concurrency, delivery recovery, multilingual retrieval, cost, and latency.
22. Production must not silently fall back to unrelated ephemeral memory while pretending writes succeeded.

KNOWN CRITICAL RISKS TO TEST, NOT ASSUME AWAY

A. The current DC_BOT topology may not justify a standalone service in the first milestone.
B. A room snapshot version is useful evidence of what generation saw, but ordinary append commits should not necessarily be rejected merely because another event arrived during generation.
C. Database and Discord delivery cannot be exactly atomic. Crash windows need explicit states and reconciliation.
D. A fixed exchange schema containing one user_event_id conflicts with multi-speaker group responses.
E. "Immutable raw events" conflicts with mutating lifecycle status unless payload, state changes, or append-mostly semantics are distinguished.
F. `discord:user:<id>` is a Discord identity. It is not automatically a verified cross-platform human identity.
G. Observing aliases on every event can create write amplification; event snapshots and current identity records should have distinct update policies.
H. Comprehensive guild member update handling can require additional Discord gateway intents and operational review.
I. Append-oriented history and privacy deletion pull in opposite directions and require a precise erasure/redaction model.
J. Arbitrary retrieval weights and latency thresholds are hypotheses until evaluated.
K. Current Airi memory work may include proposals and skeletons rather than a complete production implementation.
L. AstrBot is a useful product baseline for persisted conversations and compression, but mutable whole-history JSON is not automatically a safe concurrent-write model.
M. Multilingual and CJK retrieval cannot be hidden under a generic "PostgreSQL full-text search" claim.
